This document records the observed result without committing the bulk market-data file to Git.

## Trade callback semantics

The 49,494 Bookmap `TRADE` callbacks were not all non-zero fills.

| Trade observation | Value |
|---|---:|
| Non-zero fill callbacks | 33,292 |
| Zero-size callbacks | 16,202 |
| execution_start callbacks | 16,202 |
| execution_end callbacks | 16,202 |
| Contracts in non-zero fills | 37,130 |
| Mean passive fills per execution group | 2.0548 |
| Maximum passive fills in one execution group | 79 |
| Maximum contracts in one execution group | 100 |

The zero-size records correspond to execution-boundary semantics and should be preserved in the raw layer. A later normalized layer should distinguish `TRADE_FILL`, execution start, and execution end instead of counting every callback as a conventional trade.

All 33,292 non-zero fill callbacks in this capture contained both aggressor and passive order IDs. One passive ID was not found in the locally reconstructed active-book map at the exact check point, so passive-ID/book-state linkage should continue to be validated before making a universal guarantee.

This proves the same addon can consume a historical Bookmap replay, reach Bookmap's realtime boundary, and continue capturing live Rithmic callbacks in the same ordered event stream.

## Initial-book interpretation

At the first market timestamp, Bookmap supplied 6,721 MBO add callbacks with the same timestamp. These should be treated as initial-book population unless later API inspection proves otherwise.

Future schema work should explicitly distinguish an initial snapshot/population phase from normal post-initialization MBO adds so rate-based features do not interpret startup population as a real burst of new liquidity.

## Buffering defect discovered

During the v0.1 run, the compressed file appeared not to grow while capture was active. When the addon was stopped/unloaded, the file size increased and the summary appeared.

Root cause: event data was held behind the application's buffered writer, GZIP buffer, and buffered file stream and was only guaranteed to flush on close.

The v0.2 writer therefore adds:

- configurable periodic flushes,
- GZIP sync-flush support,
- live persisted-record count,
- live on-disk size,
- last-flush age,
- Bookmap-native status and configuration panels.

This is a direct example of the intended development process: run against real Bookmap data, record the observed behavior, fix the acquisition layer, and keep the change history visible.

## Current conclusion

The first runtime experiment demonstrated that the exporter can recover a coherent historical MBO lifecycle from the tested Bookmap recording and continue into realtime Rithmic data. The acquisition concept is therefore validated at the first integration level.

The next validation target is v0.2 runtime behavior: confirm the Bookmap settings/status panels display correctly and verify that the compressed file grows during an active capture at the configured flush interval.
